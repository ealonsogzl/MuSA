# MuSA: The Multiple Snow Assimilation system   
  
The Multiple Snow Assimilation System (MuSA), is a flexible data  assimilation toolbox for experimental and operational snowpack  reanalysis development. MuSA was designed to fuse gridded observations  with an ensemble of simulations generated by the Flexible Snow Model  [(FSM2)](https://github.com/RichardEssery/FSM2) by using different  Bayesian based data assimilation algorithms. 

In its current version, it also offers support for FSM2mem (FSM2 in Python/Numba, run in memory without the Fortran executable), SNOWPACK (it needs the `snowpack` executable in the path), the Snow17 model and a simple temperature index model (`numerical_model` = `"FSM2"`, `"FSM2mem"`, `"SNOWPACK"`, `"snow17"` or `"dIm"` in [config.py](config.py)). Potentially other numerical models could be implemented (not necessarily limited to snow models).

### Inputs  
  
The inputs of MuSA (using FSM2) are composed by meteorological forcing and  observations to be assimilated. Both the forcing and observations must  share the **same geometry**, with the same resolution and number of  cells in the latitudinal and longitudinal axes, and should be provided in the [netCDF](https://www.unidata.ucar.edu/software/netcdf/) format. Optionally it is  possible to provide a mask with the same geometry of the mandatory input  files to avoid to run MuSA over certain cells of your domain. The  meteorological forcing needed for running MuSA is composed by: 
- Incident shortwave radiation (W m<sup>-2</sup>)
- Incident longwave radiation ( W m<sup>-2</sup>)
- Precipitation  (kg m<sup>-2</sup> s<sup>-1</sup>) 
- Temperature (K) 
- Relative Humidity (%) 
- Wind speed  (m s<sup>-1</sup>) 
- Atmospheric pressure (Pa) 
  
In its current version MuSA provides support for assimilating different  variables. Note that it is possible to provide more than one of the  following variables at the same time, i.e. MuSA has support for joint  assimilation experiments. In its current version, MuSA is able to assimilate: 
- SWE (mm) 
- Snow depth (m) 
- Land/Snow surface temperature (K) 
- Fractional snow cover area (-) 
- Albedo (-)
- Sensible heat flux to the atmosphere (W m<sup>-2</sup>)
- Latent heat flux to the atmosphere (W m<sup>-2</sup>)

The support of other variables like liquid water content, density, ice content etc. is easy to implement.
  
### Data assimilation algorithms
There are different data assimilation and resampling algorithms implemented in MuSA.  Some testing should be done when developing data assimilation experiments, as the performance may be different depending on the problem to solve, and regarding the literature there is not a clear winner. Also, the computational cost will be different, and may be a strong conditioner in some situations.

Filters:
-   Particle Filter (PF)
-   Ensemble Kalman filter (EnKF)
-   Iterative ensemble Kalman filter (IEnKF)

Smoothers:
-   Particle Batch Smoother (PBS)
-   Adaptive Particle Batch Smoother (AdaPBS)
-   Ensemble Smoother (ES)
-   Iterative Ensemble Smoother (IES)
-   Particle-adjusted Iterative Ensemble Smoother (PIES)
-   Robust Adaptive Metropolis initialised by IES (IES-MCMC)
    
Resampling (for particle filters only):
-   Bootstrapping
-   Residual resampling
-   Stratified resampling
-   Systematic resampling
-   Redraw from a normal approximation of the posterior

### Outputs
The outputs of MuSA are pickles compressed with blosc, one per cell, written in `output_path` (`./DATA/RESULTS/` by default) as `cell_latid_lonid.pkl.blp`. Each file stores a dictionary containing the following dataframes:
-  **DA_Results**: Contains information about the observed variables and posterior parameters (in the normal space).
-  **OL_Sim**: Contains the reference simulation (snow simulation without any assimilation).
-  **mean_Prior**: Contains the prior mean of the ensemble (no assimilation). Not stored with `Spatial_propagation`.
-  **std_Prior**: Contains the prior standar deviation of the ensemble (no assimilation). Not stored with `Spatial_propagation`.
-  **mean_Post**: Contains the updated simulation after the assimilation, i.e. weighted mean of the ensemble of simulations.
-  **std_Post**: Contains the weighted standard deviation of the ensemble after the assimilation.
-  **mcmc_stat**: Contains the posterior mean and standard deviation from the MCMC step (only for IES-MCMC and IES-MCMC_AI).

With `write_stat_full = True` the min, max, Q1, Q3 and median of the prior and posterior ensembles are stored as well (e.g. `median_Post`). With `point_scale` or `distributed`, a cell without any observation is not assimilated: its file stores only the open-loop simulation (a single dataframe instead of the dictionary).

You can open these files by your own means, or by using the following function from the repository root:

```
from modules.internal_fns import io_read

my_cell = io_read("./DATA/RESULTS/cell_latid_lonid.pkl.blp")
```

**lonid** and **latid** are the longitude and latitude ids of each cell of the simulation.

Additionally it is possible to store the ensembles generated for each cell. This is an optional feature as it may be a bit memory consuming. However It may be useful in some circumstances specially for advanced users. The ensembles will be stored in the same format, and will containing [Ensemble objects](modules/internal_class.py).

### Usage

MuSA runs natively on GNU/Linux, macOS and Windows. MuSA relies on python3 with the usual scientific libraries (numpy, pandas, scipy...) and netCDF4 installed. You will also need to have gfortran in the path (or installed in the active conda environment). The easiest way to do this is to generate a dedicated conda environment with the [MuSAenv.yml](MuSAenv.yml) file of the repository. The same file works on every platform and already includes gfortran:

```
conda env create --file=MuSAenv.yml
```

The environment includes everything MuSA needs, including `mpi4py` for MPI runs and [SMRT](https://github.com/smrt-model/smrt) (`run_smrt = True`). To use [helpers/plot_example.py](helpers/plot_example.py) also install matplotlib:

```
conda install --name MuSA -c conda-forge matplotlib-base
```

Then for running MuSA simply, on every platform:

```
conda activate MuSA
python main.py
```

On Windows MuSA compiles FSM2 natively with gfortran. WSL, Git Bash, `make` or a Unix shell are not required. The executable, the gfortran runtime DLLs and the `spawn` multiprocessing start method are handled automatically, so `python main.py` works exactly as on Linux. Activating the environment is still recommended, but MuSA also works when the environment Python is called directly.

MPI is optional. If MPI is activated in the [config.py](config.py) file:

```
conda activate MuSA
mpiexec -n nprocess python -m mpi4py.futures main.py
```

Where nprocess is the number of threads to be deployed. `mpi4py` and an MPI implementation are already included in the conda environment (on HPC clusters you may prefer to link it to the system MPI, see the [conda-forge documentation](https://conda-forge.org/docs/user/tipsandtricks/#using-external-message-passing-interface-mpi-libraries)); the default `multiprocessing` parallelization needs neither and is fully supported on Windows.

These commands should run the reproducible example included in the repository. This example contains all the information needed by MuSA. It is composed of a few cells containing meteorological forcing and drone SfM derived snowdepth information. To change the configuration of MuSA, you should modify the [config.py](config.py) file. Also it is possible to modify the way MuSA generates the ensemble by modifying the [constants.py](constants.py) file. To run a simulation without data assimilation, use `implementation = "distributed"` (or `"point_scale"`) together with `da_algorithm = "deterministic_OL"`.
Example scripts are also provided to run MuSA in distributed supercomputing facilities using [PBS](run_PBS.sh) (Portable Batch System, not Particle Batch Smoother :wink:) or [Slurm](run_slurm.sh) job arrays. The cells of the domain are split among `njobs` array tasks, and each task runs on one node with `nprocs` multiprocessing workers:

```
bash run_slurm.sh njobs nprocs   # or: bash run_PBS.sh njobs nprocs
```

Set `parallelization = "HPC.array"`, `MPI = False` and `implementation = "distributed"` (or `"Spatial_propagation"`) in [config.py](config.py) first. The scripts check the configuration and compile FSM2 before submitting the array, and activate the `MuSA` conda environment inside each task. The environment name, memory per CPU and time limit can be changed with the `MUSA_ENV`, `MUSA_MEM_PER_CPU` and `MUSA_WALLTIME` variables, and cluster-specific options (partition, account...) can be added to the `#SBATCH`/`#PBS` lines. PBS/Slurm job arrays are only available on HPC clusters and are not used on a regular Windows workstation; use `parallelization = "multiprocessing"` there.

If the spatial propagation is activated, it is necessary to launch the pre-processor that activates the spatial prior sampling before launching the main program.

```
conda activate MuSA
python pre_main_spatial.py
python main.py
```

With `parallelization = "HPC.array"`, `pre_main_spatial.py` takes two arguments, the number of tasks and the task id (from 1): `python pre_main_spatial.py 1 1` generates all the prior maps in one process, and running `python pre_main_spatial.py njobs task_id` in `njobs` tasks splits the DA windows among them.
